## 每项需求怎么做

1. **调研和需求。** 对新的产品方向，先查已有竞品调研和实际使用场景，按需补充调研。在产品文档写明要解决的问题、适用平台和可以实际验证的完成条件。小修正复用已有结论。
2. **手机 UI 和 UX。** 在 `design/review/` 用示例数据做可点的手机画板。设计稿独立提交 Git，把直达链接发给负责人。负责人可在画板上选点批注或试改文字和字号。按编号改稿，保留落点并回传同一链接。
3. **确认和实现。** 负责人确认设计或明确说“应用到正式版”后，梳理页面、统计、存储和同步的职责，再写代码。每项功能独立提交，每次只暂存本任务的改动。
4. **验收和交付。** 用隔离数据检查正常操作、取消和失败重试。Android 使用项目自带的构建脚本 `scripts/build-android.ps1`。正式覆盖时递增 Android 版本号，用已有签名验证新包，再替换 `dist/Ztime-android-debug.apk`。保留一个正式下载入口，由负责人自行安装体验。GitHub 发布与本机覆盖分别处理。

## 需求变更、暂停和跨端交接

- 负责人中途修改正在做的同一项需求时，更新验收条件。涉及外观或交互就回到手机画板，把修订后的链接发回。明确说“先做另一项”时，记录上一项的阶段、画板或提交、未完成事项和恢复动作，然后切换新需求。
- 纯 Windows 需求回电脑版任务，纯 Android 需求留在手机版任务。配对协议、统计口径及共享 API 的改动，写明两端各自要做什么、旧版能否兼容，以及怎样验证。一个任务负责一次共享修改，另一端沿用该提交做兼容验证。
- `android/` 是 Android 原生工程；`web/` 的页面和 `shared/` 的规则同时被 Windows 和 Android 打包。手机专属行为以 Android 原生桥为边界，小窗口的 Windows 也可能很窄。改共享文件前先查当前改动，避免两边同时编辑同一段；被另一任务修改的文件和暂存内容由原任务管理。
- APK 的签名、配对凭据、TLS 文件、真实账本和本机批注都留在本机。手机任务使用测试数据，电脑版的程序覆盖和数据备份由电脑版任务负责。
