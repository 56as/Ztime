# Ztime 竞品调研报告

2026 年 11 月 1 日 · 版本 1.0 · Ztime 基线版本 0.2.3

本报告用于确定 Ztime 的产品定位、下一轮需求和设计评审重点。主要竞品为 StayFree；Apple Screen Time 作为系统级体验及 UI / UX 参考。依据为官方产品页、商店、使用指南、隐私政策和 Ztime 当前实现。本文初版是桌面研究；后续已完成 [StayFree Windows 3.8.2.0 实际点击调研](STAYFREE-WINDOWS-WALKTHROUGH.md)，更新了对会话明细、分类和限制流程的判断。初版的 Ztime 功能状态是 0.2.3 的历史基线，目标用户访谈仍未开展。

## 1. 核心结论

**建议定位：面向 Windows 与 Android 用户的开源本地时间账本。** 用户能够自己保管记录，在已配对设备之间同步，并从周报追溯到具体使用时段。

StayFree 已经免费提供跨设备统计和使用控制。因此，免费、免账号、多设备统计、CSV 导出都不足以单独成为 Ztime 的卖点。Ztime 更值得验证的组合是：源码透明、数据由用户保管、局域网连接省心、统计结果可追溯。

这个定位仍是待验证的产品假设。它是否能让用户从 StayFree 转用 Ztime，取决于用户是否在意数据保管方式，以及连接和复盘是否确实更省事。目前不能宣称 Ztime 比竞品更准确、更稳定或更安全。

## 2. 用户与竞争范围

优先研究经常同时使用 Windows 电脑与 Android 手机、希望复盘工作或学习时间、愿意自己保管数据的人。典型任务是：“周末打开手机，看懂这周电脑与手机分别用了多久，找到变化来源，并核对具体时段。”

这一人群尚未通过访谈验证。学生、自由职业者和知识工作者可作为招募来源，但职业本身不等于存在需求。招募时应确认他们最近确实尝试过查看跨设备用量，而非只表达对时间管理的兴趣。

- **StayFree：主要直接竞品。** 覆盖 Windows 与 Android，竞争的是跨设备统计、连接体验和使用习惯管理。[官网](https://stayfreeapps.com/)
- **Apple Screen Time：体验参照。** 同一 Apple 账户下的 iPhone、iPad、Mac 可以共享报告和设置；其生态范围与 Ztime 当前目标平台不同。[Apple 使用手册](https://support.apple.com/zh-cn/guide/iphone/iphbfa595995/27/ios/27)
- **其他替代方式：后续访谈观察对象。** 用户可能只看手机系统统计、分别看两端记录，或根本不复盘。不使用任何产品也会影响 Ztime 的留存。本轮聚焦上述两款产品，不据此推断整个市场规模或其他开源工具的能力。

## 3. StayFree 的能力、收费与取舍

### 产品能力

StayFree 提供跨设备用量图表、应用及网站控制，并支持立即屏蔽、定时屏蔽、每日额度和单次使用额度。Android 商店还列出免账号连接和 CSV 导出。其扩展连接指南采用六位数配对码。各平台的具体能力应分别核对，不能将官网整套功能视为每个平台都完全相同。[官网功能](https://stayfreeapps.com/) · [Android 产品说明](https://play.google.com/store/apps/details?id=com.burockgames.timeclocker) · [连接指南](https://userguide.stayfreeapps.com/settings/manage-devices)

### 收费结论

截至本次核查，官网提供免费下载，Android 页面未列出内购并声明无广告；iOS 商店标为免费。本次未发现官方公布的付费订阅方案。可以将其视为免费直接竞品，但不将“当前免费”表述为永久收费承诺。Windows 官网提供下载入口，其商店页面本轮未能完整读取。[官网](https://stayfreeapps.com/) · [Google Play](https://play.google.com/store/apps/details?id=com.burockgames.timeclocker) · [App Store](https://apps.apple.com/us/app/id1631132311)

### 开源与隐私

**完整产品按闭源对标。** 公开的 `desktop-releases` 仓库用于分发安装包，主分支仅有说明文档；未找到完整产品源码及开源许可。其适用条款授予有限使用权。这个判断不涉及其个别依赖是否开源。[官方发布仓库](https://github.com/stayfree-app/desktop-releases) · [适用条款](https://sensortower.com/panel-terms)

**本地处理与服务器数据处理可以并存。** Sensor Tower 的多产品共用政策包含 StayFree：本地处理用于提供功能，向服务器传输所列数据会请求明确同意；匿名化信息可用于商业分析产品等用途。不能从共用政策推断某次安装上传了全部数据，也不能据此认定同步一定依赖云端。iOS 版本记录还明确提到可退出数据共享并继续使用，该说明不能自动推广为所有平台行为。[隐私政策](https://sensortower.com/panel-privacy) · [iOS 版本记录](https://apps.apple.com/us/app/id1631132311)

### 可以确认的取舍与仍需实测的问题

1. **可检查性有限。** 对需要审核或修改完整产品的人，闭源是实际限制；对普通用户，这未必构成换用理由。
2. **权限范围较广。** Android 网站识别与屏蔽使用无障碍服务，授权也用于提高限额可靠性。对只想记录应用时长的人，需要衡量这些额外功能是否值得授权。[权限说明](https://play.google.com/store/apps/details?id=com.burockgames.timeclocker)
3. **存在可靠性反馈，但没有总体故障率证据。** Google Play 中有屏蔽未执行等反馈，开发者请求设备信息排查。应据此设计测试，不能把个别旧版本评论写成当前普遍缺陷。[商店反馈](https://play.google.com/store/apps/details?hl=en&id=com.burockgames.timeclocker)
4. **设备配对和跨端汇总是双方已有的能力。** StayFree 的扩展指南展示了六位码配对。对于已配对的 Windows 和 Android，下一步应在保留局域网、断开互联网的条件下分别从两端发起同步，核对新记录是否到达对端。StayFree 在这个场景下的表现仍待实测。[StayFree 设备连接指南](https://userguide.stayfreeapps.com/settings/manage-devices)

收费不是已证实的短板；不能为了突出 Ztime，把 StayFree 已有的跨设备、导出或免账号能力写成缺失。

## 4. Ztime 当前差异与自身短板

以下“已有”以 0.2.3 实现和项目文档为准，真实网络及 Android 后台表现仍需现场验收。[产品开发文档](PRODUCT-DEVELOPMENT.md) · [项目说明](../README.md)

### 已有能力形成的差异

- **MIT 开源。** 用户可以在遵守许可的前提下检查、修改和分发源码。相对于 StayFree 完整产品，这是明确差异，但并非整个市场的独有优势。[许可](../LICENSE)
- **本地账本与局域网同步。** 两端保存 SQLite 记录，无账号、遥测或云端账本；配对后的数据通过 TLS 在局域网交换。数据保管方式清晰，用户同时承担备份和设备安全责任。
- **可追溯的应用记录。** 保留应用起止时段、设备来源，可导出 JSON / CSV；支持自定统计日界线和时区、上周同期比较。应验证用户能否借此解释用量变化，不能直接推断竞品没有等价明细能力。
- **按应用采集的较小权限范围。** 当前不采集网址、窗口标题、消息、截图或键盘内容。Android 统计使用情况需要系统授权，扫码另需相机权限。其代价是无法判断浏览器内具体课程与娱乐页面。

### 已确认目标，但尚未交付

**连接省心：已配对设备回到可互访的局域网，在任意一端点击一次同步。** 两端先更新各自的记录，再交换变化并展示最近成功时间。0.2.3 的手机端可以发起同步；电脑端目前提示等待手机连接。电脑主动触达手机及后台响应还需要架构验证。

同一个 Wi-Fi 名称不保证设备可互访，访客网络隔离、电脑休眠和手机后台限制都会影响连接。设计应解释实际状态并提供重试，而不是一律显示“已连接”。[同步目标与验收条件](PRODUCT-DEVELOPMENT.md)

### 待验证提案

StayFree 官网列出按类别设限，Mac 浏览器扩展的商店说明还明确支持自建类别用于限额。尚待在 Windows 和 Android 核实的是，用户能否回到历史记录，把同一个网站的两次访问分别归为学习和娱乐，并与另一台设备的学习记录合计。[StayFree 官网](https://stayfreeapps.com/) · [扩展的分类与限额说明](https://apps.apple.com/de/app/stayfree-track-block-sites/id6468659272?mt=12)

**按行为复盘。** 让用户把词典、课程相关记录归为“学习”，查看归类原因，并修正误归类时段。目前尚未实施行为分类或网页识别。应先用已有应用数据和手动修正验证价值，再决定是否增加网址采集；“分类”本身不作为独创卖点。

### Ztime 必须承认的不足

- 应用屏蔽、每日额度、网站识别、家长管理尚未实现；需要这些能力的人可能更适合 StayFree 或系统工具。
- Windows 记录前台时间，不因无键鼠输入而停止，不能把结果宣传为专注时长。两端同时使用会累计两份时间，不计算个人净时长。
- Android 受事件历史、后台调度和省电策略影响，长时间停采可能缺记录。
- 本地数据库没有额外加密；暂无云端备份和跨互联网同步，设备丢失与自行备份是实际使用成本。
- 双端一键同步还未完成，当前发布的 Android 包为调试签名版本，发行与安装体验仍需完善。

## 5. Apple Screen Time 的 UI 与 UX 参考

Apple 提供日／周摘要、常用应用、拿起次数及通知次数，并通过小组件、周报通知提供回访入口。这些做法可用于研究信息层级和逐步查看细节的流程。[Apple 摘要与入口](https://support.apple.com/zh-cn/guide/iphone/iphbfa595995/27/ios/27)

Ztime 的下一轮设计建议如下，均先进入设计稿评审：

1. **首屏回答核心问题。** 优先呈现选定时间范围、设备累计时长、同期变化和数据更新时间；复杂模块放到后续层级，默认布局应在无需编辑时也易读。
2. **形成连续的查看路径。** 总览 → 某天或某应用 → 原始时段 → 返回原筛选条件。用户能解释数字来源，不需要在多个页面重新选日期。
3. **统一视觉规则。** 时长单位、日期范围、同一设备或应用的颜色保持一致；桌面利用宽度并排展示，手机保留清晰的单列阅读顺序。
4. **补足跨设备状态。** 明确区分“今天没有使用”“手机尚未同步”“权限未开启”和“记录中断”。各设备显示最近成功时间，避免将数据缺失误读为零。
5. **把同步结果设计完整。** 覆盖等待、同步中、已完成、已是最新、离线、拒绝、超时及重试。完成提示必须对应两端实际确认的结果。

设计交付物应包含 Windows 与 Android 的总览、周报、应用详情、设备同步、设置，以及关键异常状态。每个画板有稳定编号；批注记录位置、操作路径、问题和期望，修改后在同一处复核。现有可批注原型可继续承载这一流程。

Apple 有系统级数据和控制能力。Ztime 当前不能把窗口切换次数当作拿起次数，也不能在没有采集能力时展示通知次数或承诺相同的系统管控效果。

## 6. 下一轮验证计划

以下是建议的研究门槛，不是已经获得的结果，也不是市场统计结论。

### 竞品实测

- **首次连接：** 用同一组 Windows 与 Android 设备，记录安装、授权、配对的步骤数、耗时、失败点；分别测试两款产品。
- **互联网依赖：** 完成配对后保留局域网、断开互联网，在两端新增记录并尝试同步。再独立测试首次配对是否依赖互联网，避免混淆两种场景。
- **恢复与一致性：** 更换 IP、锁屏、休眠、取消权限后恢复；观察是否需要重配、是否重复计时、是否正确传播删除及显示更新时间。
- **统计口径：** 手工记录一次电脑使用 30 分钟、其中 10 分钟同时使用手机的实验。分别核对设备时长、合计与显示说明，不预设竞品采用哪种去重方式。
- **授权选择：** 记录 StayFree 数据共享的默认选项、拒绝后的功能变化、撤销入口。平台、版本及所选功能均写入测试记录。

每项结果附版本、系统、网络条件、复现步骤和观察记录。真实 Android 设备由项目所有者操作验收，研究结论不以构建成功代替实机结果。

### 小样本用户验证

邀请 5 位符合目标场景的人。先了解其最近一次跨设备复盘经历，再用同一组示例数据交替展示不同方案，以减少顺序影响。

- **理解：** 至少 4 人能够独立找到变化最大的应用，指出其来源设备，并分清“尚未同步”和“零使用”；记录完成时间及误解。
- **连接：** 原型中至少 4 人能在首次配对后找到同步入口，并理解失败后该做什么；真实联网另行验收。
- **选择理由：** 让参与者在 StayFree 与 Ztime 方案间选择并解释理由，记录是否主动提到本地保管、连接或明细，不先灌输这些卖点。
- **持续价值：** 一周后询问是否主动复盘、遇到什么新问题。若只有口头兴趣而没有再次使用，应重查任务价值。

这些门槛用于发现明显设计问题，5 人样本不能估计市场占有率、付费率或长期留存。若用户持续追问学习目的且愿意修正记录，再为行为分类编写独立 PRD。

## 7. 产品开发建议

**先验证连接与复盘，再扩大功能范围。** 建议下一轮 PRD 聚焦首次配对、后续单次同步、数据更新时间、周报来源和明细返回路径。将“同一局域网任意端发起”列为需技术验证的体验目标。

开源是信任基础，不能替代稳定性和易用性。StayFree 当前免费，因此 Ztime 的付费能力不能从竞品价格空档推导；本轮不提出未经验证的订阅价格或收入预测。

后续按已约定流程推进：**市场调研 → 产品需求 → UI 设计稿与 UX 原型 → 软件架构 → 编码与验收。** 新需求先在设计稿上提出和修改，原型状态确认后再确定实现方案。行为分类、网页识别、强制限额和 iOS 接入分别评估，不自动纳入本轮开发。

## 8. 依据与维护

主要外部依据已在对应结论旁链接。定价、权限政策及平台能力在正式确定 PRD 和对外宣传前应重新核验。原始专题分析保留在 [Screen Time 与竞品调研记录](SCREEN-TIME.md)，实现状态以 [产品开发文档](PRODUCT-DEVELOPMENT.md)、[README](../README.md) 和源码为准。

本轮没有执行竞品安装、真实网络对照或用户访谈；没有据此声称发现独占市场、确定用户付费意愿或证实竞品同步缺陷。后续实测应更新相应结论及日期，保留观察条件。
